# 设计：端到端加密（团队 Hub 可选）

状态：第一期已实现（v0.18.8 起）。

## 1. 已定的取舍

- **默认不开启**。个人用的 Hub（自己的电脑或自己的 VPS）没有必要：Hub 就是自己的。
- **按 Hub 开启**，由 Hub 的所有者在 App（设置 → 安全）或命令行（`myco hub settings --e2e on`）打开。适合几个人共用一个 Hub 的团队。
- **只有当事人能读**：一条消息只有收发双方，以及双方节点的**主人**（他们的 App 设备）能解密。Hub、Hub 的管理员、其他成员都读不到。
- 开启只影响之后的消息，**不加密已有的历史**；关闭后新消息恢复明文，已加密的仍然只有当事人能读。

## 2. 防什么，不防什么

防：
- Hub 所在机器被入侵、数据库或备份泄露、VPS 服务商。
- 团队里的管理员或其他成员翻看别人节点之间的对话。
- 局域网模式（明文 HTTP）上的窃听。
- Hub 伪造或篡改消息：每条消息由发送方签名。

不防（Hub 必须知道才能转发）：
- 元数据：谁和谁通信、时间、消息大小、类型、线程、状态。
- 节点名、描述、标签和公开的状态行（`agent status`），这些本来就是给大家看的。
- 已被入侵的端点（拿到了某台机器上的私钥）。

## 3. 密钥

每个**身份**一对密钥：X25519（加密）+ Ed25519（签名），在本机生成，私钥不离开本机。

| 身份 | 私钥存放 | 公钥登记 |
|---|---|---|
| 节点（agent） | 节点的 profile `~/.myco/agents/<name>.yaml`（600） | 注册 / 入网 / `myco join` 时，或 `PUT /v1/me/keys` |
| App 设备 | App 的钥匙串（和控制台令牌放在一起） | 配对时（`POST /v1/console/pair` 带上公钥） |
| 命令行加入的成员设备 | `machine.yaml` 的 `member_key`（600） | `myco member accept` 时 |

- Hub 只存公钥：`agents.enc_key / sign_key`，`console_tokens.enc_key / sign_key`。
- 旧节点没有密钥：升级后 runner 启动时自动生成并登记，无需重新入网。
- 私钥丢了（profile 被删）：重新生成一对；之前发给旧密钥的消息就读不了了。这是端到端加密的代价，App 里写清楚。

## 4. 一条消息加密给谁

发送方 S 发给接收方 R 时，读者集合 =

1. R 本身（节点密钥；R 是 `@console:<成员>` 时，是该成员的所有设备）；
2. S 本身（自己发出的消息以后还能在 `message thread` 里看到）；
3. S 的主人的所有设备，R 的主人的所有设备（去重）。

读者集合由发送方向 Hub 查询（`GET /v1/keys?for=<R>`，返回上面各项的公钥），在本地组装。

**信任**：第一次见到某个身份的公钥就记下来（`~/.myco/known_keys.json`，App 也有一份），以后变了就醒目提示并拒绝自动使用，类似 SSH 的 known_hosts。已知的限制：恶意的 Hub 可以给某个成员“添加”一台假设备来多收一份；第一期靠「我的设备」里出现陌生设备、以及其他人看到的“某某新增了设备”提示来发现，第二期用设备互相签名（新设备的公钥由同一成员的已有设备签名）堵上。

## 5. 加密格式

和 age 相同的思路（每条消息一把随机内容密钥，再分别包给每个读者）。只用 Go 标准库：X25519（`crypto/ecdh`）、HKDF-SHA256、AES-256-GCM、Ed25519。实现在 `internal/e2e`：

```
body = "myco-e2e:v1:" + base64url(json{
  "k":   [{"id": "<读者 key id>", "epk": "<临时 X25519 公钥>", "wk": "<包裹后的内容密钥>"}, ...],
  "n":   "<nonce>",
  "ct":  "<AES-256-GCM(内容密钥, 明文载荷)>",
  "sig": "<发送方 Ed25519 签名>"
})
```

- 明文载荷是 JSON：`{"body": "...", "attachments": [{file_id, name, size, sha256, content_type, key}]}`。
- 签名覆盖：from、to、type、thread_id、reply_to、nonce、密文的哈希。接收方用 Hub 登记、并且本地已记下的发送方公钥验证，失败就当作无效消息并提示。
- 附件：文件内容用各自的随机密钥加密后上传，Hub 存的是密文；文件名和大小这类元数据只在加密载荷里，Hub 上记作 `encrypted`。
- API 的 `Message` 多一个 `e2e: true`，`body` 就是上面的信封。Hub 原样存储和转发，不解析。

## 6. 各部分怎么变

- **CLI**：`message send / reply / hold / fail / progress / steer`、`broadcast send` 在 Hub 开启了加密、且读者都有公钥时加密；`inbox pull`、`message get/thread` 自动解密。`--format json` 输出解密后的内容，加 `"e2e": true`。
- **runner**：把解密后的内容交给 CLI；自动回复、进展、失败原因都加密。exec 节点的命令和结果同样加密。
- **广播**：本来就是一人一条，逐条按各自的读者集合加密。
- **失败事件**：`fail --reason` 由失败方加密，Hub 生成事件时原样带上信封。
- **App**：解密在 App 的本地后端（Go）里做，私钥不进网页。对话、当前工作、与其他节点的往来、节点详情里的摘要都显示解密后的内容；读不了的（不是当事人）显示“已加密，只有双方的主人能看”。消息旁边有锁标；未加密的消息在已开启加密的 Hub 上标“未加密”。
- **搜索**：Hub 读不到正文，对话搜索改成 App 在本地对已加载的消息搜；Hub 端的 `q=` 只对明文消息有效。
- **浏览器直接打开 Hub（`myco ui`）**：没有密钥，加密消息显示“已加密”，看内容用 App 或 CLI。
- **GitHub webhook 回复**：外部发不了加密消息，作为明文接收并标“未加密”。

## 7. 兼容和过渡

- 旧版本客户端（没有密钥）：发给它们、或由它们发出的消息只能是明文，界面标“未加密”。Hub 的 `GET /v1/keys` 让发送方知道谁还没有密钥。
- 第二期加一个“必须加密”的开关：打开后 Hub 拒收明文（GitHub webhook 除外，或单独开关），节点要先升级。
- 关闭加密：只影响之后的消息。

## 8. 实现顺序

**第一期**
1. 密钥生成、存放、登记（节点、App 设备、命令行成员设备）；`GET /v1/keys`；`known_keys` 和变化提示。
2. 信封格式和签名（`internal/e2e` 包，带测试向量）；消息正文、进展、修正、失败原因的加解密。
3. 附件加密。
4. Hub 设置 `e2e`（所有者可改，审计 `hub.e2e`）；CLI、runner、App 接入；锁标和“未加密”提示；App 本地搜索。
5. 文档：INSTALL 的团队一节、api.md、本文。

**第二期**
- 密钥指纹查看和核对；设备互相签名。
- “必须加密”开关。

## 9. 测试

- `internal/e2e`：加解密往返、多读者、篡改检测、签名校验、错误密钥、固定测试向量。
- 集成测试：开启加密的 Hub 上，A 的节点发给 B 的节点：B、A 的主人、B 的主人都能读；第三个成员、Hub 管理员令牌、直接查数据库都只能看到密文；旧客户端回退明文并被标记；公钥被替换时拒收并提示。
