# myco App UI design spec

Read this before adding a page, component or dialog. It describes what the App (`web/src/app`, the interface in the Wails window) does now; the values are defined by the variables at the top of `web/src/app/app.css`, and this document only explains how to use them.

The classic `myco ui` (`web/src/App.tsx`, Tailwind theme) is not covered by this spec.

## 0. Concepts: the only things the user sees

Treat the user as someone who is not technical. Only these words appear in the interface, and each one is the user's own concept:

| Called in the UI | What it is | What it is underneath (appears only in the CLI and in a member card's "Details") |
| --- | --- | --- |
| **Workspace** | A team's space, holding projects and members; one used by a single person is "My workspace". Workspaces are fully separated: only one is shown at a time, and after switching, every page, dialog and filter covers only that workspace; there is no "All workspaces", and the user is never asked to pick a workspace again | Hub |
| **Project** | One thing to get done, and the members doing it together | project |
| **agent** (member) | An AI colleague with a name, an avatar and a role | node (AI session) |
| **Computer** | A real computer that is connected: a laptop, a cloud server (VPS) and a WSL install each count as one. Agents run on computers; the computer itself decides which folders agents may start work in and the highest access they get | machine (and its machine node) |
| **Terminal** | A folder on a computer where an agent runs commands; open it and you can watch | shell / exec node |

- Words such as node, machine, Hub, runner, allow_from and token do not appear in the main flows.
- **One computer can have several workspaces** (`myco hub up --name`). The interface still only says "workspace": in the switcher, the workspaces on this computer carry a small "This computer" tag, and the menu has "New workspace on this computer" (it asks for the workspace name first; the internal name is generated: an English name becomes a name of lowercase letters and hyphens, a Chinese name becomes `ws-2`, `ws-3`, counting up from the existing ones; once it is up, the App joins it and switches to it). Settings has "Workspaces on this computer", one row each, showing the name, the address, the reach (this computer and local network only, Cloudflare, Tailscale), and "Open to the internet" and "Stop" (with only one, it is the same as before). On first use, with no workspace yet, the one-click start on the welcome page is still used.
- **Resume**: a cloud agent's sandbox is temporary, and its credentials get lost. In the member card and in an AI colleague's details, "Identity and binding" has a "Resume" row, visible only to people who can manage that agent. With no link yet, it shows one line of explanation and "Make a link"; with a link, it reads "Last resumed X ago · in <sandbox>" or "Not used yet", followed by "Make a new link" and "Revoke". After a link is made, a dialog gives a command to copy (`curl -fsSL … | sh`) and explains: send this line to that agent, or put it in its project instructions or memory; it runs it once in the new sandbox and is connected again; the line is as good as a credential, so do not make it public. Before making a new link or revoking, say first that the old link stops working at once. When the workspace is too old to have this link, the row is not shown.
- **Model, reasoning effort and quota**: in "Runtime", an agent woken by the runner whose CLI is Claude Code or Codex has three things. Model and reasoning effort have a row each, showing the value in use and where it comes from (App settings / reported by itself / seen in the last turn…); people who can manage it change the value to one from a dropdown (for Claude Code: fable, opus, sonnet, haiku; for Codex: the current value and a few common names; plus "Custom…"), or choose "Follow this computer", and after a change one line says "takes effect the next time it wakes". Reasoning effort for Claude Code is Low/Medium/High/Very high/Max; Codex adds "Minimal". Quota has one row per window, for example "5 hours: 62% used · resets 3:40", "7 days: 58% used · resets Friday"; at 90% or more it is amber; when used up it is red and says "Out of quota; resets X"; when the data is more than an hour old, a line below adds "data from X ago". On the Computers page, the agent rows of this computer also carry a small hint when quota is tight. An agent that receives inside its session (inbox wait) gets only one line, "Its own session manages the model and quota; myco can't see or change them.", and when model_source is self, the model it reported itself is shown; when the workspace is too old to have this settings API, no editing controls are given, only a read-only display.
- **Welcome page** (`Welcome.tsx`, the whole window while there is no workspace yet, modelled on Kettu's first screen, 2026-11): two columns. The left column (at most 520px wide): the logo at the top left; in the middle a two-line large title "All your AI agents, / in one network" (34px, weight 650, tightened letter spacing), one line of explanation, a large primary button "Start on this computer →", and under it a line of small text "No server or account needed: one click and it works"; then a thin divider with "Or", and under it two quiet text entries (no icons, a › on the right, a background on hover): "Join a workspace" (opens the connect dialog) and "Let my agent set it up" (expands that sentence and a copy button in place); at the very bottom, on the left "Open source · Data and tokens stay on this computer", on the right the language segmented control (System / 中文 / English). On the right, a rounded canvas (dot-grid background, a very faint touch of blue and of green in two corners) draws the product itself: a small window, with three members of a project on the left (pixel mushroom avatars, Claude / Codex badges, what each is doing) and a chat on the right (your message, ticked steps, a breathing dot on the step in progress, the agent's reply and three screenshot placeholders), and a "PM to Docs" handoff card floating at the top right; below it, one line "Each works on its own computer". All of it is built from the interface's own parts: no screenshots, no coloured icon blocks, and colour comes only from the mushrooms. On entry, the text and the picture float up gently one after another (no motion when reduced motion is on). When the window is narrower than 980px, the right side is not drawn and the left column is centred.
- **Bottom of the welcome page**, on the right, two small segmented controls: appearance (System / Light / Dark, three icons, the name on hover) and language (System / 中文 / English); a choice takes effect at once, and they are the same switches as in Settings.
- **Set up this computer** (`Prepare.tsx`, modelled on T3 Code's welcome page and Kettu's "Your agent is ready", 2026-11): on a newly installed computer, it appears after "Start on this computer" on the welcome page, once the workspace is up (kept on this computer as `myco-prepare`, cleared only when finished or skipped; if the App is closed midway, it appears again next time); Settings › About › "Getting started · Open" opens it again (for the current workspace). The same two columns as the welcome page. Left: the small text "Your workspace is running", the large title "Set up this computer", one line of explanation (use the Claude Code and Codex you have already installed and signed in to, with the subscriptions you already have); an "Agent CLIs" card (the same rows as Settings › Agents: ready / installed but not signed in / not installed; the buttons open a terminal to install or to sign in, and it checks again by itself when you come back to the window); a "Bring in sessions you have" card: the Claude Code / Codex sessions a person started on this computer that are not in any workspace yet, most recent first, all in a scrollable box about five rows tall (it never makes the whole page longer); with more than 8, the top of the box has a search (title, folder, CLI) and "N picked"; each row has a square checkbox, the session's first sentence (the folder name if there is none), and below it a line folder · Claude Code / Codex · how long ago; of the last three days, at most two from different folders are ticked in advance; what joins is a copy (`fork`), and the original session is still yours. With none at all, one line says "Inside, Add agent starts a new one". At the bottom, a semi-transparent fixed bar: on the left "You can add more any time with Add agent.", on the right "Skip for now" and the primary button "Add N and start →" (with nothing ticked, "Start"; while adding, "Joining 2/3…"). Sessions that fail to join stay in the list, still ticked, with the reason below; the rest have joined. When done, it goes to "Conversations" and opens the chat with the first agent that joined. The canvas on the right draws the sidebar's "Conversations" as it will look after joining: one row per ticked session (pixel mushroom, the name "folder (Claude Code)", the first sentence), one more row for each tick; grey placeholders when there are fewer than three rows, and below, one line "Inside, they are in the sidebar".
- **Workspaces in onboarding** (2026-11): a new user needs to know what a workspace is (where your agents meet: agents connected to the same workspace, on whichever computer, can hand each other work and do projects together), where it runs, how to let other computers and colleagues join, and that more can be created or joined. The small text under the welcome page's primary button says "It starts a workspace on this computer, where your agents meet". At the top of the Set up this computer page, "Your workspace": one line on what it is, a card (initial square, name, "On this computer · This computer and local network only"; when it is not opened up, "Let computers outside connect" on the right opens the Open to the internet dialog), and below it three lines of small text: other computers connect under "Computers › Connect a computer", colleagues use an invite link, and to keep things apart, create or join another one from the workspace menu at the bottom left; the title bar of the small window on the right canvas shows the workspace name, and below it one line "Inside, they are in My workspace". The third step of the getting-started checklist, "Meet your workspace", opens Settings › Workspaces (in simple mode too: a section that is explicitly sent to appears in the navigation for the time being); opening that page ticks the step (when Settings is already open, it switches there directly), and the first time, that page has an intro card.
- **New project** (`NewProjectForm` in `AddToProject.tsx`; the sidebar's "+ New project", ⌘N and the getting-started checklist all open it): the dialog has one line of explanation (state the goal clearly and add the materials, so the coordinator and members know from the start what to do), and three fields from top to bottom: project name (required); goal (optional, a three-line text area whose example reads "what, by when, and what counts as done", with small text below: "The coordinator and members all see it; change it any time in Project notes"); files (optional): a dashed box "Drop files here, or click to choose" (requirements, designs, conventions, screenshots, each up to 20 MB); chosen files are listed one per row (file icon, name, size, × to remove); a file over 20 MB is marked red, and the primary button is greyed out with an explanation. With files, the primary button reads "Create, with N file(s)"; in progress it reads "Creating…", "Uploading files 2/3…". Files are uploaded after the project is created; if some did not upload, the dialog changes to one line "The project is made, but N file(s) did not go up", lists them, and offers "Go in; upload later" or "Try again".
- **Getting-started checklist** (`Checklist` in `Onboard.tsx`, modelled on Kettu's SetupGuide, 2026-11): a small card at the bottom of the sidebar, above the workspace switcher. It appears only on a newly installed computer (started from the welcome page, or from Settings › About › "Getting started · Open"; kept on this computer as `myco-onboard`). The title "Getting started 2/5", a fold arrow and × (don't show again), and below them a thin progress bar (black; green when everything is done); expanded, it shows six steps, each with a circle, a name and one grey line of explanation: Connect your first agent, Give it something to do, Meet your workspace, Have two agents work together (start a project), Set up an automation, Connect another computer. Done steps tick themselves (judged from the workspace's data: there is an agent, you have sent a task, there is a project with two or more members, there is an automation, there are two or more computers): the circle becomes solid and the text is struck through and greyed. Clicking a step not yet done goes to do it (opens Add agent, the chat with the first agent, New project, the Automations page, Connect a computer). When everything is done, it shows "All done" and "Put it away". The folded state is kept on this computer.
- **User guide** (`Help.tsx`, content in `web/src/app/help/zh` and `help/en`, one Markdown file per page, built into the App, 2026-11): read as a documentation site: on the left a search box and the pages in groups (Getting started, with workspaces right after the introduction; Workspaces and network; Working together; Computers and terminals; Automation; Getting more out of it; More), the one shown with a background; on the right the page as a document (`.fp-doc`), "Previous" and "Next" at its foot. A page links another as `[text](#help/<id>)`, opened in place. Narrow windows pick the page from one list above it. It opens from the the last row of Settings' nav ("User guide", with a small ↗: it leaves Settings for the guide's page; not in the workspace menu), Settings › About, the Mac's Help menu, and the last step of the getting-started checklist ("See what else myco does", ticked once the guide was opened); the page last read opens next time. A page is written for someone doing it: what it is and when you need it, then steps in the order people meet them, with the real labels (checked in the code), and screenshots: `![what it shows](shot:<name>)` names a UI test screenshot (`ui-smoke/1200x800-light-<name>.png`); `node scripts/help-shots.mjs` (after `UI_SMOKE_SCALE=2 node scripts/ui-smoke.mjs --combo 1200-light`) makes it a WebP in `help/img`, bundled with the App. Pictures are as wide as the text, framed like a window, and open full size on click (← → through the page's). A new feature gets its page (or a section) here, in both languages, with pictures.
- **Feature intro cards** (`IntroCard` in `Onboard.tsx`, modelled on Cindy's first-time feature intros): also only on a newly installed computer; the first time you enter a project's home page, Apps, the Computers page or Settings › Workspaces (and the Automations page when it has automations), a card under the page header: one bold line "X: what it is for", one or two lines of explanation below, "Got it" on the right, and on the Computers page also "Connect a computer". Once clicked, it never appears again (kept on this computer as `myco-intro-seen`). When the page has its own empty-state explanation (no automations yet, no computers yet, workspace too old), it does not appear, so nothing is said twice.
- "Automations", "Workflows", "Apps" and "Computers" at the top of the sidebar (and "Needs you", 待处理, when it is shown again: see below); for the pages: clicking one again while already on that page goes back to its list (closing the automation or computer that is open).
- **Examples in an empty chat** (`EmptyChat` in `ConversationDetail.tsx`, modelled on Cindy's home-page suggestions): under the large avatar and an opening question, three lines of things to click (with an agent: Show me around this project, Review my uncommitted changes, Write an AGENTS.md for this repository, Run the tests… 8 in all; with a project coordinator: Break this project into steps and hand them out, Ask each member what they are working on… 6 in all), each on a card background with a ↗ on the right; a click puts it in the input box (cursor at the end), to edit and then send; it is not sent directly. Below: "Others · Don't show again"; "don't show again" is kept on this computer (`myco-starters-off`).
- **Simple mode** (`simpleMode.ts`, a switch in Settings › Appearance): on by default for new users who started with one click from the welcome page, off by default for users who already have a workspace. When on, it hides the sidebar's "Terminals", "New workspace on a server" in the workspace switcher (joining or starting one on this computer stays: onboarding sends people there), and Members/Audit in Settings (My devices, with Add another device, then shows at the foot of Settings › Workspaces, so one person can still add their phone; the Workspaces page is not hidden: when there is only one workspace on this computer, Open to the internet, Rename and Stop are also there); it only hides, it deletes or changes nothing. In Add agent, the computers, Connect a computer, and AIs in the cloud or elsewhere are not hidden: even a single user often has a cloud server.
- **Open to the internet dialog** (`PublicAccessDialog` in `SettingsPage.tsx`, class names `pub-*`; do not use `pa-*`: that belongs to the pixel avatars): three option cards (One click, "Recommended"; Cloudflare with your own domain, "Fixed address"; Tailscale Funnel, "Fixed address"); the selected one has a black outline and a solid tick on the right; one whose tool is not installed is faded and says what to install; your own domain is filled in inside the card. After "Open", the cards are replaced by progress: a spinner, "Opening with Cloudflare…" and a seconds count, a thin progress bar moving back and forth, three numbered steps (download or start cloudflared, open the tunnel, get the address and confirm it can be reached; for Tailscale: turn on Funnel, request a certificate the first time, get the ts.net address), and one line "Usually 10–60 seconds. Cancel if you would rather not wait: the workspace keeps working on this computer and its network." On success it does not close by itself: an "Open to the internet" card (green tick), the public address and the join link on a row each, with copy, a reminder, and "Done" closes it.
- **Settings is a dialog** (`SettingsDialog` in `AppMode.tsx`, modelled on Kettu, 2026-11): ⌘,, "Settings" in the workspace menu, the command palette, update prompts and the getting-started checklist all open it; it covers the current page (semi-transparent overlay; the dialog is 44px from the window's top and bottom, at most 1040px wide, radius 16), the page underneath does not move and is where it was after closing. The left column holds the "Settings" title, search and the grouped navigation (a slightly darker background), the right side the content, with ✕ at the top right. Esc (which first clears the search box when it has text) or a click on the overlay closes it; menus and small dialogs opened from Settings sit above it (layers: page ≤ 51 < Settings 55/56 < menus, dialogs 60+). In a narrow window (below 820px) the dialog fills the window and the navigation becomes a row at the top. Opening another page closes Settings automatically.
- **Structure of the settings page** (`SettingsPage.tsx`, modelled on the settings pages of Kettu, t3code and Cindy, 2026-11): the navigation on the left is grouped: "This computer" (Appearance, Voice, Translation, Proxy, App permissions, Agents), "Workspace" (Workspaces, Members, Audit; in simple mode only "Workspaces" remains), and, last and on its own, "About". At the top of the navigation, a "Search settings" box (⌘F / Ctrl+F on the settings page focuses it): every word typed must match (Chinese and English both work, for example "字号" (font size) or "proxy"); the navigation becomes a list of results, each with the setting's name and the page it is on; clicking one, or Enter for the first, switches to that page, scrolls to that row and makes it flash twice (`data-setting` on the row; new setting rows must carry it too and be added to `FINDABLE`); Esc clears it. Each page starts with a title and one line of explanation (`.app-settings-head`), followed by uniform setting rows: the name and one line of explanation on the left, the control on the right. In a narrow window the search box takes its own row, group titles collapse, and tabs wrap.
- **App permissions** (Settings › App permissions, `AppPermissionsSection` in `SettingsPage.tsx`; the question itself is `osWant` and the consent `Modal` in `pages.tsx`): before a page uses a group of this computer's capabilities, a small dialog asks "Let "<app>" <do this>?" with "Don't allow", "Allow this time" and "Always allow" (the primary; only "Allow" for exec, delete and screen, which are allowed for this run only), a line when the app did not declare it, and where to take it back. The settings page lists each page that was allowed or refused something: a row with its name, workspace and "Take all back", then one indented row per permission (what it lets the page do, in plain words; "Always", "This time, until the App quits" or "Refused") with "Take back" ("Stop refusing" for a refusal); empty, it says when the App asks.
- **Agents on this computer** (Settings › Agents, `LocalAgents.tsx`): one row each for Claude Code, Codex, Gemini CLI and opencode on this computer: icon, name, one status line (Ready · version / Installed, not signed in / Installed, whether it is signed in cannot be told / Not installed), and on the right a status pill (Ready, Signed out, Installed, Not installed) and a button: "Install" when not installed (a dropdown when a China mirror exists: the official way / China mirror), "Sign in" when not signed in or when it cannot be told. The button opens a terminal window that runs that command, and the row says "Opened in a terminal… it checks again by itself when you come back here"; if no terminal can be opened, it gives the command with a copy button. It checks again when the window regains focus, and "Check again" is at the bottom. When it cannot tell whether it is signed in, it does not say "Signed out", so something that works is not shown as unusable.
- **Run access**: the access in "Runtime" shows the level actually in use (Read-only / Workspace / Full), with "(App)" when the App has an override. Only the agent's owner can change it; an agent with no owner is changed by the workspace owner, and admins have no extra right to change it. The options include "Follow this computer"; the cap is the higher of the cap the computer reports and the actual access, and higher options are greyed out with an explanation to set `spawn.max_access` in `~/.myco/machine.yaml` on that computer; this computer keeps the "Allow on this computer" entry. An old runner that reports no cap is read-only, with a prompt to upgrade. Choosing "Full" first confirms that there is no sandbox and it can read and write any file; after saving, it takes effect at the next wake, with no restart.
- Names: an agent uses the display name it chose itself (the joining sentence asks it to write its role with `--display-name`); without one, "<folder> assistant" (`myco assistant`; in Chinese `myco 助手`), and duplicates are named "#2", "#3" in the order they joined (in Chinese "二号", "三号"). A computer is "computer name · folder" (`Studio Mac · myco`). All of this is in `nodeName()`.
- Avatars: each agent is a pixel mushroom (`Avatar` in `persona.tsx`); cap colour, spots and expression are set by its id and are always the same; the stem is a warm beige with its right edge in shade (`--av-stem`, `--av-stem-shade`) so it stands out from the pale tile in light mode, and cream in dark mode; the small badge at the bottom right is Claude (orange asterisk) / Codex (white >_ on a blue-violet circle); the small dot at the bottom left is the status. A computer's avatar follows its OS: Mac is an apple (graphite grey in light mode, silver in dark mode), Windows is a four-colour 2×2 grid, Linux (WSL included) is a penguin (in dark mode its body is a little brighter, so it does not blend into the background), and an unknown OS or a cloud machine is a terminal screen on black. A person is a circle with the first character of their name. Avatars can be changed (`AvatarPicker.tsx`): in a member's profile card, clicking the large avatar (a small camera appears at its bottom right on hover) opens "Change the face": at the top a preview with "Use a picture" and "Back to the original", below it "Or pick a mushroom": a row of 10 cap colours, a grid of 12 looks (spots × expressions), and "A sprout on top". The App crops a photo to a square from the centre and scales it to 256px before sending it. The chosen avatar is stored on the workspace, so everyone sees the same one; computers and people can only use photos. When the workspace version is too old, it says "This workspace's myco is too old to change faces." The workspace's own avatar (the initial in a coloured square): in Settings the pencil opens "The workspace's name and face": 8 colours or a photo, stored, like the name, only in this App.

## 1. Principles

1. **Like a native tool, not a web admin panel.** The cursor is an arrow, not a hand; hover gives feedback at once, with no transition; buttons have a pressed state; anywhere a right-click makes sense, it works.
2. **Quiet.** The interface is neutral grey. Colour is kept for things that carry meaning: status, links, dangerous actions. At most one solid button per screen.
3. **Few lines.** Hierarchy comes from lightness and spacing, not from borders and dividers.
4. **One thing, one look.** One colour per state, one meaning per shape, one style per kind of button.
5. **Use what exists first.** When the classes and components listed below are enough, do not write a new set.

## 2. Layout

The window opens maximised (filling the screen, not full screen), like Codex and Claude; un-maximised it is 1200×800. On a Mac with a notch, while members are working, a "notch island" shows at the notch; it can be turned off in Settings ("Notch island" on/off). Pointing at it expands it into who is doing what, and clicking a name opens the App at that agent:
- **Already on screen: nothing moves**: when its chat is showing (the coordinator on a project's home page, a member in the right column, a full-page one-to-one chat), the App only comes to the front and the border of that column flashes once; no page change, no scrolling (you may be reading back).
- **Not on screen**: if the space you are looking at (a project or "Chat") has it, it opens in that space; otherwise it goes to the project of the work it has in hand; otherwise to any project it is in; if there is none, in "Chat". Opening a member in a project works as usual: the coordinator stays on the left and members go in the right column; the coordinator is the project's home page.
- The island never shows "0": the number is how many agents are at work (shell nodes running commands are not counted), and with nobody at work it folds away (while it folds, the last number stays). A workspace that cannot be read for a while (a bad network) keeps who was at work there, so the island does not flicker in and out; someone who starts and stops before the window is ready leaves it folded away (`Island.tsx`; the UI smoke "灵动岛 · 不显示 0").
- The App catches the click at the native layer and hands it to the page (`mycoWatchClicks` in `island_darwin.go`): the island is a panel that does not take focus, and the web page itself swallows the first click, using it only to focus the window, which is why clicking a name used to do nothing.

```
└─ Content panel (--bg), 8px around it, radius 10px, thin outline --panel-shadow
   ├─ Top bar 40px (36px on Mac, aligned with the traffic lights): sidebar toggle + page name (not on project pages: the project name is below)
   └─ Page
```

The sidebar can be dragged wider: moving the mouse to its right edge (the gap between it and the panel on the right) shows a grey line; drag to adjust the width, 200–420px, leaving at least 520px for the page on the right; the width is kept in this App; double-click the edge to restore the default (232px); dragging all the way to the left and releasing collapses the sidebar, and reopening it restores the earlier width. With keyboard focus on the edge, the left and right arrow keys also adjust it.

A project page is the last two of the three columns (`ProjectSpace.tsx`): in the middle, your chat with the coordinator (when a member is opened, the middle splits again into left and right columns); on the right, 248px of members and computers, and the button next to the heading collapses it into a 56px-wide strip of avatars only (hover to see the name and what it is doing; the collapsed state is remembered). Below 900px wide the right column collapses and the members become a row of avatars under the title. Members are in one order everywhere (`orderMembers`): the coordinator, those at work (the latest to start first), those with work queued, the idle, the offline; within each, the most recently active first (what it last reported, its tasks, the project conversations it took part in, when an away one was last seen).

- Page content uses `.app-page`: at most 880px wide, centred, padding `18px 20px 40px`.
- The first line of a page is `.app-page-head`: a one-line summary on the left (`.app-summary`), the page's "New" button on the right.
- When two columns side by side are needed (list + details), build them like the chat page's `.conv-split`, with only one divider between them.
- Details use the right-hand overlay (`.app-inspector`): 420px wide, 8px around it, radius 10px. The header is a single row: icon, name, status, close.
- There are three surfaces in all, from dark to light: window `--chrome` → panel `--bg` → card `--card`. Do not add a fourth.

## 6. Components

### 6.1 Buttons

Choose by "how important this action is, and where it is", not by taste.

| Class | Looks | When to use |
| --- | --- | --- |
| `.app-btn.app-btn-primary` | Solid, near black or near white | The confirm button of a dialog; "New X" in the header of a top-level page; the main action of a details page ("Run"); the guiding button in the middle of an empty page. At most one per screen |
| `.app-btn` | Grey background | Cancel, secondary actions, ordinary buttons in cards |
| `.app-btn.app-btn-quiet` | Normally only an icon and text; a faint background and a thin border only on hover | "New"-type actions at the top of a page (add node, add machine, New task, Invite a member) |
| `.app-group-action` | Small text button, faint background on hover | Actions to the right of a section title (Edit, Upload, All, Refresh) |
| `.app-btn.app-btn-plain` / `.conv-head-icon` | A 16px icon in a 26px square | Icon-only buttons; must have `title` and `aria-label` |
| `.app-btn.app-btn-danger` | Light red background, red text | Remove, delete, and the confirmation of dangerous actions |
| `.app-summary-action` / `.app-kv-link` | Green text | Real links: going somewhere else, an inline "View" |

- Every button has four states: hover, pressed, disabled and keyboard focus; the classes above come with them.
- When a button cannot be clicked, say why: in a dialog, with `.app-modal-hint` to the left of the button.
- Button heights come only in these sizes: default 26px (`.app-btn`, used in page headers, dialogs and cards alike), small 22px (`.app-btn-small`, in list rows). Do not give buttons a height of their own on some page; an icon-only button (⋯) is a square as tall as the buttons next to it.
- When one button has two or three choices, use one button with a dropdown menu (`useContextMenu().openUnder`), not two buttons side by side.

### 6.2 Inputs

- Text boxes are `.app-input`, dropdowns in forms `.app-select-field`, search in toolbars `.app-search` and filters `.app-select`. All have a grey background and no border.
- Focus is a 1px neutral thin line (`--focus`), with no glow.
- Wrap a field in `label.app-field`, with its label in `.app-field-label`. Required fields get no asterisk; optional ones say " (optional)" in the label.
- By default a form shows only what must be filled in. The rest goes in `details.app-advanced` ("More: …").
- For a choice of two or three, use the segmented control `.seg`. Tabs in a dialog use `.seg.seg-fill` to fill the row; in Settings they are as wide as their content and aligned right.
- To turn an option on or off in forms and settings, use the switch `.app-switch` (`role="switch"`, with `aria-label` saying what a click does); on is green. List rows and details headers get no switches: disable / enable, pause and the like go in the ⋯ menu. Options in forms still use checkboxes.

### 6.3 Lists and rows

- A group of rows goes in one card: `.app-list` holding `.app-row` (nodes, machines) or `.conv-row` (chats).
- Row structure: an icon on the left, two lines in the middle (title 13/500, description 11.5 grey), status or a count on the right, and at the far right a `›` (`.app-chev`) meaning it can be opened.
- Hover is a rounded band of colour; selection is a fill one step darker. No colour bar on the left.
- Status in a row is a small dot, never a colour change of the whole row. An offline row drops to 55% opacity as a whole.
- Group titles go above the card, outside it (`.app-group-title`), with room for section actions on the right.

### 6.4 Key-value tables

"Name–value" pairs in details use `.app-kv`: a grey label on the left, the value aligned right. IDs, paths and commands get `.mono`. A value that can be clicked is followed by `›`.

### 6.5 Dialogs

Use `Modal` and `ConfirmDialog` from `dialogs.tsx`; do not write your own overlay.

- The title says in one sentence what is to be done; one line of explanation may follow below it.
- Buttons go at the bottom right: "Cancel" first, then the confirmation. The confirm button names the specific action ("Start session", "Remove"), never "OK".
- Reminders inside a dialog (for example "Let agents run commands on this computer") use `.app-notice`: grey background, a small shield or info icon, normal text colour; no red block (`.app-warn` is no longer used for such reminders).
- **Adding a computer to a project**: at the top, "Computers you already have" (computers in the workspace that are not in this project yet), one row each; "Add" adds it in one click and lets the project's agents send it commands; below, "Or use another folder on a computer" is the way to start a new one.
- Dangerous actions use `ConfirmDialog` and stay **calm**: the title is a short question ("Delete this agent?", "Disconnect it?"), with no long ID stuffed into it; `subject` holds one line for "who" (avatar + display name, the ID in small monospace below); `description` says in one or two plain sentences what will happen, and `consequences` is one lighter extra sentence (for example "Your chats with it are kept."). **No red warning blocks**: red is kept only for the confirm button (light red background, red text).
- Action rows in details (`.app-action-row`) each start with an icon; a row with a current value (for example "Who can give tasks · Anyone") puts the value before the arrow. Dangerous rows (`danger`: disconnect, delete) normally have the same colour as the other rows, turn red only on hover, and have no arrow (a click asks for confirmation first).
- Deleting a machine is not like deleting a node: first get the nodes that would be deleted with it via dry-run, list them by display name in the dialog, and state "The N nodes on this machine are deleted with it; chat history is kept"; if the machine is still online, add a line: the runner on that computer will be refused and stop, and to uninstall it completely, run `myco runner service uninstall` on that computer (the command in `.app-command` with a copy button). The confirm button states the number ("Delete the machine and N nodes"). The entry is under "Actions" in the machine's details, as `.app-action-row danger`, shown only to the machine's owner, the Hub owner and admins; after deleting, close the details and refresh the list.
- A dialog resets its fields only when it opens, never on each render or poll.
- **Spacing**: 14px between the explanation under the title and the content (`.app-modal > p`); 16px between the content and the bottom buttons (`.app-modal-actions`); the buttons do not touch the dialog's bottom edge (the dialog's own padding takes care of that; do not remove it). When a form is long enough to scroll, the bottom button row sticks to the bottom (`.au-actions`), visible wherever you scroll to.
- **Tabs**: tabs in a dialog (`.seg.seg-fill`) have no divider between them and the content below, only 14px of space (`.add-pane`). Every tab has the same order: a short label (`.app-field-label`, saying what you are to do, one line at most), then the content (options, command, the sentence), and last a line of small text (`.app-small-note`: how long it is valid, who can see it, caveats). Do not write long explanations as labels.
- **Status goes to the left of the button**: waiting ("Waiting for it to join; its chat opens then", with a spinner in front), what is still missing, why it cannot be clicked: each goes in one `.app-modal-hint` line to the left of the bottom buttons, not in a paragraph of its own.

### 6.6 Context menus

Every clickable row has a context menu, built with `useContextMenu` from `ContextMenu.tsx`.

A menu stays open when another panel scrolls (including a streaming chat), or when its own items scroll. Scrolling a container of the source row closes it because its anchor moved.

- The first item is what a left click does ("Open", "View details").
- In the middle, the object's other actions.
- After a divider, the "Copy …" items.
- A dangerous item is marked `danger`, goes last, and is named by the action itself ("Delete", not "Delete this workflow…"; a click asks for confirmation first). Normally it has the same colour as the other items, and only turns to red text on a light red background on hover or keyboard selection.
- Unavailable items are greyed out (`disabled`), not hidden.

### 6.7 Labels

- Status uses `.app-pill` (with a dot, fully rounded): `green` / `amber` / `red`, or the default grey.
- Groups and `#标签` (#tags) use `.app-label`.
- At most three labels shown in one row.

### 6.8 Empty states

- A whole page that is empty: `.app-empty`, one icon, one title line, one line of explanation, at most one solid button.
- A search or filter with no results gets its own wording ("No matching nodes"), not the same sentence as "No nodes yet".
- Empty inside a card: one `.app-empty-note` line.
- A large blank area with nothing selected (the right side of the chat page): a very faint logo as a watermark, with one line of hint.

### 6.9 Hints and errors

- Inline errors use `ErrorText`: first say what happened, then what can be done. Cannot reach the Hub and Hub version too old have ready-made wording; do not give the user the raw error.
- Warnings use `.app-warn` / `.app-notice` (an orange icon with one sentence).
- Loading uses skeletons (`Skeleton.tsx`), shaped like the loaded content. No full-page spinner.
- A page remembers its content once seen (kept in memory per workspace): coming back shows the last content at once and refreshes in the background; skeletons appear only the first time. The spacing between skeletons is the same as in the loaded content (section titles are held by `SectionSkeleton`); do not cram them together.
- The two top-level pages Automations and Apps have the same content width (at most 1000px), with their left and right edges aligned.
- Page data refreshes itself (every 5 seconds); do not add a refresh button; ⌘R / Ctrl+R refreshes at once.

### 6.10 Terminal

Traffic with exec and shell nodes uses `Terminal.tsx` (`.term`). It is dark in both the light and the dark interface, with its colours in `.term`'s own variables. Your own session and watching another node look the same:

- It fills the whole panel below the title bar, with no card, margins or dividers.
- Text is 12px monospace with a fixed 17px line height (`ui-monospace`, SF Mono on Mac), no ligatures. `.term` does not use the global `antialiased` and keeps the system's own font smoothing, so light monospace text on the dark background does not look thin.
- Each command is one line, "`❯` command", with its output directly below; 8px between two commands. `❯` is green and drawn with `PromptSign` (SVG, one character wide); do not type the character: it looks different in every monospace font.
- Commands are the brightest layer (weight 500), output clearly one step dimmer, "who · time" and hints one step dimmer again. No large areas of near-white text on near-black: it is tiring to read for long.
- Output is shown as it is; stderr is not marked red. When the previous command failed, the `❯` of the next prompt turns red; no labels or red borders.
- An overlong command is folded, ending in an ellipsis; click the command itself to expand it, and again to fold it (on hover the command line has a very faint background). No separate "Expand" button row.
- A line wraps only at the right edge, and may break in the middle of a word, as in a terminal.
- While a command runs, a blinking block cursor follows the output.

The two situations differ only in these points:

**Your own shell session** should work like a terminal:

- The prompt is preceded by the working directory in blue; the last line is the input line; clicking anywhere on the panel focuses it, and ↑↓ go through the command history.
- Sender, time, duration and exit code are not shown (hovering over the command line shows them).
- While a command runs, the bottom status line becomes "Running · Ctrl+C to stop".
- `clear` (or Ctrl+L) is handled by the App itself, not sent to the node: earlier content moves off screen, and a dim line at the top can be clicked to bring it back. The clear is kept on this computer (`localStorage`) and still holds after the App restarts.

**Watching another node run commands** is a record: it must be clear who ran each command, and when:

- "Who · time" is written in the small interface font above a run of commands, like grouping in a chat: it is written again only when the sender changes or more than 10 minutes have passed, with a little more space above. The duration is in the command line's hover tip.
- Commands always show on one line only (three lines in your own session): a record is for scanning, and a neat column of commands reads better than a sprawl of long wrapped ones.
- Output longer than 7 lines shows only the last 6 (how the command went is usually at the end), with a dim line above, "… N more lines above"; a click shows all of it.
- A failed command gets one line in dark red under its output, "exit N". Do not put this to the right on the command's own line: once the command is long, it is pushed onto a line of its own, between the command and the output, which looks messy.
- No input line; below the panel is a "View only" notice bar.

**Commands other agents sent to this computer that may be stuck** are not in the terminal (the terminal shows only your own traffic); a thin amber strip below the title bar explains them:

- One line, "N commands on this computer may be stuck (from X, Y)", with an amber dot in front, followed by "Show" and (when you have permission) "Stop all".
- "Show" lists them one by one: the command (just the source when there is no content), the source, how long it has been quiet ("quiet for 1 h"), and a "Stop" for each. A command shows on one line only, cut short with an ellipsis when too long, with the full text on hover.
- Stop buttons are shown only when you can manage this computer or it is yours; otherwise there is only the hint; when stopping fails, the error goes in the strip.
- Commands you sent yourself still use the chat's own line, "May be stuck", with "Stop" and "Resend"; they are not repeated here.

The small dots for computers, projects and chats in the sidebar work the same way: a green dot while some work in progress is not stuck; when all the work in progress may be stuck, an amber dot instead (`title` says "May be stuck"), and no green dot.

### 6.11 Chatting with an agent

Your own chats ("Mine") are an agent chat window (`ConversationDetail.tsx`, `TraceView.tsx`), not the left and right bubbles of a messaging app.

- One column, at most 760px wide, with the input box the same width.
- What I say is a small bubble on the right (`--pill` background, radius 16). The agent's reply has no bubble: the text fills the whole column, laid out as Markdown.
- What the agent did (the process) sits between my message and its reply, on the left, laid out as in Claude Code and Codex: what it says along the way is shown directly as body text (Markdown), not folded; its thinking counts as process, and together with the run of steps between two pieces of text (running commands, reading and editing files) it folds into one grey summary line ("thought, ran 3 commands, edited 1 file"), expanded only on a click (expanded, thinking is one line with a brain icon; click again for the full text); there is no longer a paragraph of faint text in the body. While running, the line for the newest run says "what it is doing now", with a walking mushroom in front and the elapsed time after; it **never expands by itself**. When it ends, the last line, in small text, is the duration and tokens. Steps are marked only "still running" and "failed"; success gets no tick.
- Progress (`myco message progress`) is one grey line on the agent's side.
- "At work" counts only tasks the node has accepted (acked): when a task is still delivered (pulled by inbox pull but not acked yet) or held (accepted, to do later), it is treated like a queued one: the node does not count as working, the list says "Queued", the chat says "Waiting" and "Queued; it starts when its turn comes", with no spinner and no "In progress"; the node's "Queued" count also includes delivered tasks.
- When an accepted task has had no activity for a long time (10 minutes for a node woken by the runner, 30 minutes for a node that receives only in its session, at once when the node is offline; counted from its last activity: the task itself, the progress it reported, the steps of its process, whichever is latest), the result may have been lost: no "In progress" and no spinner; **below** its process one line is added, "No activity for X hours; it may be stuck (the result may not have come back)", followed by "Stop" and "Resend"; what it did and said before (steps, progress, its words) stays in the process as usual, rather than leaving only a few progress lines. If it ended the turn itself, or put the task on hold (waiting for you or for someone else), it does not count as stuck and the line is not shown (except when the node is offline); this holds for every stuck task in the chat, not only the newest. Lists, node rows and details mark it separately as "May be stuck", not counted under "In progress". The right of the chat's title bar **no longer shows** states such as "Done / At work / Session in use" (the mushroom and the hint at the bottom of the chat already say this); only when there is a task that may be stuck does it show "May be stuck", which jumps to that task when clicked. The phone (iOS) uses the same rule (`activity`, `ended` in `ConversationBuilder.items`): counted from the last activity, a task whose turn has ended counts as waiting, not stuck (except when the node is offline); for a task not yet closed, its process is fetched however old it is, or waiting could not be told from stuck. A task whose reply is already in the chat no longer gets a stuck hint, and the input box is not aimed at it. When judging whether it is waiting (`RunProcess.isPaused`), first drop, as on desktop, the turns in which it woke only to keep receiving messages (`myco inbox wait` and the like): an agent that said one line of progress and went back to `myco inbox wait` counts as waiting, with no loading below it, and the input box is not in "add to" mode with stop. The round button turns into stop the instant a message is sent, so a click within 1.5 seconds after sending does not stop (so that a double click does not stop the task just sent).
- **No "stuck" on a poor network**: "how long it has been quiet" counts only up to the last time data was fetched and does not keep rising with the current time: when no new data comes in, the agent may be working all along, and only its messages did not get through. While it is working and the chat's own polling has had no response for 20 seconds or more (failed, or never answered), the area above the input box becomes one light hint line (amber no-network icon, `.conv-behind`): "Poor connection: this chat hasn't updated for N; the agent may well be at work. Retrying by itself.", followed by "Retry" (not shown when it has stopped and the chat has no task in progress: there is nothing to wait for); meanwhile "May be stuck" is not shown and you are not pressed to stop; once data arrives, the hint goes away by itself. The "May be stuck" of the sidebar dots, member details, the Conversations list and the terminal works the same way, counted from the time each workspace last had data (`seen_at`). The App's read requests (GET) wait at most 60 seconds (100 seconds for the long poll of web page data); a request that never answers is given up, and the next round refreshes as usual: otherwise one stuck request would hold up every later refresh, leaving the interface on old data until a restart. When a whole refresh round fails, every workspace is marked "Can't reach it · showing N ago", the same as when a single workspace cannot be reached.
- Times and the copy button are normally hidden and appear only when the mouse is over a message; messages on both sides can be copied; failed, stopped and encrypted marks are always shown.
- Names are shown only when watching the traffic between two nodes, and then both sides use bubbles. Consecutive messages from the same side form a group, and the name is written only on the group's first message.
- When watching, progress does not take a line of its own: while the task is in progress, the newest progress is the text of the "Working" line at the end of the chat; once there is a reply, progress folds into one line above the reply, "N progress updates", which opens to show all of them. Do not leave a line of progress alone between the bubbles of the two sides, where nobody can tell who said it.
- When a reply (`reply_to`) does not come right after the message it answers (for example the other side sent several tasks in a row), the top of the bubble quotes the original message: a vertical bar on the left, the sender's name and the first line of the original; a click jumps there and makes the original light up briefly. A question and answer right next to each other get no quote.
- On the left is a column of ticks (`TurnRail.tsx`), one for each thing you said: the one you are at is longer; hover shows that turn's question and answer, a click jumps there. It has a narrow lane of its own and does not cover the text; it is not shown with fewer than two turns. When watching two nodes, one tick is one task, and the preview says who sent it. Terminal-style chats have no tick rail.
- **The agent's suggested next step**: when replying, an agent can give one sentence of "what you may want to say next" (`myco message reply --suggest`, `myco message suggest`, stored on that task). When the newest task in the chat carries a suggestion, the agent is not working and the input box is empty, the placeholder becomes the suggestion (one line only: measured against the input box's width, cut short with "…" when it does not fit; Tab fills in the whole sentence), and below the input box a hint says "Tab to use the suggestion"; Tab fills it into the input box, to edit and then send. Without a suggestion, everything is as usual. The phone (iOS) has no Tab: the suggestion is shown in a line above the input box ("Suggested: …"), and a tap fills it into the input box.
- **The round button to the right of the input box follows the state** (modelled on ChatGPT, Claude and common chat apps, 2026-11): with nothing in the box it is **voice chat** (waveform icon; only in the Mac version, and only when both the model and Doubao voice are set up in Settings › Voice; otherwise it is send, as usual; you talk with this chat's agent, see "Voice chat" below); with text or attachments it is **send** (↑); while the agent is working and the box is empty it is **stop** (■). The microphone (speech to text) is always to the left of the round button and does not go away with text or attachments (the Claude desktop app drops the microphone once there is text, and users complained they could not go on talking). **Hold ⌥Space** (Mac) or **Ctrl+M** to speak, and release to stop (on Windows ⌥Space opens the window menu, hence Ctrl+M). The hint text under the input box is normally hidden and appears only while the agent is working ("Enter to add · ⌘↩ to queue": without the hint nobody would know). The input box on a project's home page works the same.
- While running: when the input box is empty, the send button becomes stop. While this turn is not yet answered, the input box talks to **this turn**, as in Codex and Claude Code: the placeholder reads "Add to X… (⌘↩ queues the next one)" (Ctrl+Enter on Windows and Linux), Enter **adds** the words to the task in progress, and ⌘/Ctrl+Enter **queues** them as the next message. The target for adding is the most recent of your own tasks in this chat that has no reply and has not failed or ended, even when the newest task has been answered. With no task in progress, both kinds of Enter send a new message. There is no separate "Working" line.
- **Adding** (`steer`): it goes into the original task, not a new turn; it is no longer labelled as an addition (what it is is obvious), and the part that continues in the task bubble shows only the time at its top; the task still has only one spinner/status, and the other side takes it as the same matter continued. Files go along with it (workspace v0.19.2 and later; earlier workspaces have nowhere to put them, so it is sent as a new message instead). **Everything is in time order**: when the task has a process and no other message lies between it and this addition (a task you sent, or one someone else gave it, in the member view), the addition goes into this turn's process, inserted by the time it was sent among its steps and progress; when other messages already lie between (another task, its answer, including this task's own answer), the addition is drawn where it was sent (at the very bottom), quoting the task it adds to at its top, and does not jump back up into the process; the task's process then stops at the time it was sent, and what the agent does after it (steps, progress, the loading) goes on under it, not above it (UI smoke "项目 · 插话排在后面"). In the process it is a small bubble on the right (no label), as in Claude Code and Codex: what it did before the addition is above, and what it did after and its current state (spinner or "Waiting") are below. A task without a process (encrypted, may be stuck): when nothing lies between the addition and the task, it continues in the task bubble; when other messages lie between, it is drawn where it was sent, quoting the task it adds to at its top (like a reply that does not come right after; a click on the quote jumps back). When other messages already lie below a task that is still running, the reply text it is writing does not grow up there; when the reply arrives, it appears at the bottom in time order.
- **Find in the chat** (`ChatSearch.tsx`): ⌘F (Ctrl+F on Windows) or the magnifier at the right of the chat header floats a search bar at the chat's top right: it searches as you type, starting from the newest message; Enter moves up to the previous match, ⇧Enter down to the next, Esc closes. It searches the messages of the chat on screen (yours, its replies, additions); every match is marked in light amber, the current one darker, and it jumps there with a flash. On the right it shows "2/5" or a red "No match"; when earlier messages are not loaded yet, there is also "Look further back". With two columns side by side, ⌘F goes to the column clicked last.
- **Replies grow only while you watch** (`Reveal`): replies that already exist when the chat opens (those in the first load, however long it took; or ones written more than half a minute before opening) are shown whole at once and not replayed next time; only those that arrive while you have the chat open grow in bit by bit.
- **Sending** (`pending` in `ConversationDetail.tsx`): what you send shows at once at the end of the chat as your bubble, a little faint, with a small spinner and "Sending…" under it on the right; the box is empty again straight away (no spinner in the send button). When the workspace has it, its copy takes the bubble's place; if it does not go, the bubble goes, what you wrote (and its files) goes back into the box, with anything typed meanwhile after it, and the hint below shows. One put after the running round (⌘↩) is not shown as sending: it goes straight into the "Queued:" list above the box (its Edit and Withdraw come once the workspace has it). A group's box (`Composer` in `ProjectSpace.tsx`) does the same with a faint task card at the end of the feed. Coming back to a chat, a running task's steps and when it last did something are shown as last read (kept while the App is open), so it is not shown empty, or as quiet ("No activity for …"), for the second its trace takes to be read again.
- **Not sent** (`SendTrouble`): when sending times out or cannot connect, first wait a moment and check on the workspace whether the message actually arrived (the same text, sent by you, just now); if it did, treat it as sent; only if it did not, show a light red hint **above** the input box: "Not sent The workspace can't be reached right now, or is answering too slowly. What you wrote is still in the box.", with "Retry" and × on the right; the raw error (such as context deadline exceeded) is visible only on hover. A failed stop works the same way ("Did not stop"). No more red English text under the input box.
- **Images retry before failing**: when an image in the chat (a message attachment, an image in the text) fails to load, it is tried again after 1.2 seconds and after 2.4 seconds, and only then shows "Image didn't load · click to retry" (in the text) or turns into a file row (attachments).
- **Scrollbars**: on Mac, the system's own (thin bars that appear only while scrolling). On other systems (WebView2 on Windows shows wide, always-visible scrollbars with arrows by default) the App draws its own: thin, no arrows, normally invisible, appearing when the mouse is over something scrollable or while scrolling, and hiding again a moment after scrolling stops (`main.tsx` adds `os-other` to `html`, and `is-scrolling` to the element while it scrolls; the styles are at the end of `app.css`). Elements that set their own `scrollbar-width` (such as horizontal tab strips) follow their own setting.
- **Windows icon** (`cmd/myco-app/build/windows/icon-256.png`): on the taskbar it is only twenty-odd pixels, beside icons that fill their square (Chrome, the Terminal). So on Windows there is no tile: the mushroom alone fills the picture edge to edge, ink outline with cream spots and stem and a thin cream rim, as the notification-area icon is drawn, so it reads on light and dark taskbars alike (a cream tile vanished on a light taskbar and left a small black mushroom). The Mac icon keeps the tile and the margins of Apple's grid.
- **Show / hide is grey**: "Show all (N lines)" and "Show less" under a long reply are small grey text that darkens on hover, not green; green is kept for small accents such as status dots and the tick for done.
- **Opening does not jump**: when you open something in a chat ("Show all (N lines)", a turn's steps, a folded part), the extra content grows downward in place and the view does not move; even if you were at the bottom a moment ago, it does not follow down to the very end (once you have opened it you count as having left the bottom: new messages no longer take you down automatically; use "Back to the bottom", below, to go back).
- **Back to the bottom**: when you scroll up far from the bottom (more than 400px), a round down-arrow button floats up at the bottom centre of the chat; if new messages arrive meanwhile, it turns into an "N new" pill. One click scrolls smoothly to the bottom and the button disappears.
- **Position when a chat opens**: a chat you left at the bottom is at the bottom when you open it again; one you left while scrolled up comes back to where you were reading (remembered while this window stays open). Only your own scrolling (wheel, touch, dragging the scrollbar, keys) counts as leaving the bottom: content above loading in (steps, pictures), or the browser shifting the view so the content does not jump, never leaves the chat stopped in the middle. When you jump to a message or to a task that may be stuck, that smooth scroll also counts as your own scrolling.
- **Progress-only steps** (Settings › Appearance › "Steps in chats": "Everything" / "Progress only", stored on this computer): with progress only, each turn in a chat shows only the progress the agent itself reports with `myco message progress` (text, checklist plans, screenshots) and the choice cards it asks you with; thinking, commands and the text it writes as it works are not shown. The little mushroom shown while it works still appears, and replies show as usual.
- **Queued**: a message sent with ⌘/Ctrl+Enter is held back; it is sent automatically once this turn's answer is done, without interrupting it. Above the input box, one line per message: "Queued: " plus the message's first line (if it has only files, "(files)"), with "Edit" and "Withdraw" on the right (a line is at least 34px high and the buttons 26px, so they are easy to hit); you can queue several in a row, and they are sent in order. "Edit" withdraws the message and puts its text and attachments (pictures, files) back in the input box (the sentence written automatically when there are only files is not put back); "Withdraw" means it is not sent. Messages queued before this turn ends do not mix into the chat; only after it ends do they become an ordinary new message; a queued message that was withdrawn or edited away and never sent will not show up in the chat later as "Stopped". From workspace v0.19.2 the workspace keeps the queue (the messages carry `after`); with older workspaces the App keeps it (`queued.ts`; like drafts it follows the session and is still there after reopening), and it is sent automatically just the same; in both cases the strip above the input box looks the same.
- When watching two nodes, as long as there is a task without a reply (judged by `reply_to`, not by what the last message is), the end of the chat shows a "Working" line (`Working.tsx`) on the side of whichever one is doing the work: a pixel mushroom (myco is mycelium) marching in place and puffing spores, followed by the node's name, what it is doing and for how long; if more tasks are queued behind it, it says "N more queued". The line appears only when it is really working: if the task is still queued, or a newer one is the one being worked on, it is not shown. What it is doing: the task's latest progress, then the status the node reports (`status_text`); if there is neither, a random playful verb ("Mulling it over", "Growing mycelium", "Tinkering"…), changed every 3.6 seconds. If the node is offline, or the task has been open for more than 12 hours, it is not shown. Your own tasks do not get this extra line (nor, in a member view, do tasks others sent it; they already have their own steps below them): the little mushroom sits at the very start of the running-steps line, in place of a spinner. While a task is queued the steps show nothing (see the receipts below); once it is picked up but has no steps or progress yet, it says "Picked up, starting Claude Code / Codex" (the name is left out when the CLI is not known), with the state updated by the steps poll every 1.5 seconds; once there is activity but for the moment no step, it shows a playful verb; when there are steps, it shows the current step; then comes the elapsed time, counted from the start of this turn: the latest of the task being sent, your last addition, or the first step after it stopped and started moving again (for a task open for half an hour, if you have just added a sentence, the timer starts again from that sentence). **Only one loading indicator moves in a chat at a time**: when several tasks are still open, only the newest one being worked on (picked up or with progress reported) shows the walking mushroom and the current step; the earlier ones that are still open no longer show anything. The "Working" line for someone else's task at the end counts too: whichever is newer moves. A chat has **at most one mushroom**. **Working and stopped are separate**: if the task is still open but the agent is no longer producing output, it does not count as working: no spinner, and nothing is added at the end of the steps (see the next item). What counts as no longer producing output: its turn has ended (`turn_end` from `trace follow`, or the runner's `usage` once a whole turn has run); there has been no new step since it was put on hold; or the last thing it did was talk or think, followed by no activity at all for 2 minutes (a command still running does not count: however long it runs, that is working). If after that there is again a step that really does something (not just talking), or it reports progress again, it counts as working again. A session waiting in `myco inbox wait` wakes up on a timer to wait for messages again (or to pull or ack the next one); a turn that only ran `myco inbox wait/pull` and `myco message ack/done/release` does not count as working and is not shown in the steps (`withoutChores`; newer CLIs do not upload it through `trace follow` at all, see `trace_chores.go`). The input box and the loading indicator use the same check (`atWork`): when it stops, both stop (the input box is the plain "Message X…", with no loading indicator), and when it moves again, both move; a task on hold counts as working only once it has really done something after the hold in the steps: progress saying what it is waiting for, work it sent out, and the hold itself (`myco message hold/progress/send/ask`) do not count; the skill tells the agent to put the task on hold first and then report a line on what it is waiting for, and that should not leave a spinner going (`isWaitStep`). **The loading indicator follows the bottom**: when the task being worked on already has other messages below it (work it sent out, your additions), the spinning mushroom does not stay at the end of the steps (it would sit above the card for the work it sent out) but goes to the very last line of the chat (name, playful verb or latest progress, elapsed time).
- **Long sessions are shown by time**: an agent waiting in `myco inbox wait` is one continuous session: you send the next message, it picks it up and carries on, but its steps and progress are often still recorded under the task it picked up first (which is still open). The chat is ordered by time: a task's steps are shown only up to your next message (`until`); once your message has been picked up, the steps and progress that the earlier, still-open task adds after it are shown under your message (`borrow`), not up above, and the bottom is not left with nothing but an idle loading indicator. Agents woken by the runner finish one task before taking the next, so they are not affected. The phone (iOS) uses the same rule (`RunWindows`): progress goes with the turn it appeared in; while your message has not been picked up (queued, not delivered), nothing moves; a command that started before your next message and ended after it keeps its result on the command's side, and does not keep showing as "still running" up above.
- **Messages that were not delivered**: a task the workspace gave up delivering (`delivery attempts exhausted`) does not show the reason as it is; it is written in plain words: "Not delivered: it picked this up several times but never started on it. Its session may not be running, or may be stuck. Send it again, or check that it is online first." Below it is "Send again": it sends the same message (text and attachments) to the same agent again, in the same chat, and the failed one stays. A timeout reads "Timed out: …" and other failures "Failed: …", and these can be sent again too; one you stopped yourself reads "Stopped", without this button. The phone (iOS) is the same (`FailureWords`, `ConversationModel.sendAgain`), and notifications use the same words; tasks sent by others and read-only pages have no "Send again".
- **Strictly by timeline**: after you send a new message, whatever the agent says or does next (steps, progress and screenshots for the previous task) appears below this message; it does not go on growing above it. The previous task's steps stop before your message; what follows goes below your message: if it has already started looking at this message, that counts as this message's steps; if it has not yet, it starts with a line of small light text, "Still on the one before: <first few words of the previous task>", and your message gets "Queued behind the current one" under it. The loading indicator is at the very bottom of the chat. The answer to the previous task still appears below in time order, with a quote at the top saying which message it answers. The loading line at the very bottom says what it is doing **now**: its latest progress (whichever task it belongs to); if it has answered since, it uses its reported status or a playful verb instead, rather than staying on what it said when it picked up that task; the timer counts from the latest message in the chat (think of a coordinator working all the time in one session: its early task stays open while it goes on answering new messages). The phone (iOS) is the same (`RunWindows`, `ConversationBuilder.items`): the previous task's steps are cut off at your next message and what follows goes under it; while it has not been picked up, that section starts with "Still on the one before: …"; replies and additions that do not directly follow what they refer to get a light quote line at the top ("In answer to: …", "Adding to: …"); the loading line at the very bottom gives its latest progress (or its status or a playful verb if it has answered since), with the timer counting from the latest message in the chat; for an agent that receives messages in its session, the receipt reads "Delivered" until it has looked.
- **Tasks read as messages, not as statuses**: the chat has no status lines such as "waiting", "not done yet", "waiting for X to finish" or "set aside for now": the user cannot tell what it is waiting for and only feels it is stuck. When it stops, nothing is added to the steps; the last thing it said is its answer, as in a chat. For a task not started yet, a receipt in small light text always shows under your message (before the time): "Not opened yet"; while one ahead of it is being worked on, "Queued behind the current one"; when the node is offline, "Offline; it reads it when back"; when the session is in use, "Its session is busy elsewhere"; when the runner is not running, "Its runner is not running" (hover for the full reason); when it is on hold (`myco message hold`), "Will answer later". Once it starts (picked up or progress reported), the receipt disappears. "May be stuck" still has a line of its own, because it carries "Stop / Resend", which are things the user can do.
- **On-hold tasks**: show a receipt under the original task, and a separate
  on-hold status in conversation rows and the member's current work. A delegated
  task says “On hold: waiting for another agent to reply.” A question names the
  sender who can answer. With no known dependency the receipt says
  “On hold · no one is working on it.”
- **What the superagent needs your OK for** (`ApprovalStrip` in `Superagent.tsx`): only in the chat with your superagent (Shroom), above the input box, one light amber card per item (`.sa-approval`, icon `ShieldQuestion`): "Shroom wants to: <what>", the reason it gives, how long it is still valid, and "Deny" and "Approve" on the right. Each card is decided on its own: while one waits for the workspace to answer, only its own buttons wait (its "Approve" spins) and the others can still be clicked; once decided it goes at once, the list read again behind, and an error shows on that card. Once handled, the card disappears and the Hub sends the agent a note from you with the outcome (with the ids it needs); in the chat that note is one quiet centred line, "✓ You approved: create the scheduled task "x" of project "p"" (or "You declined: …", "…, but it did not go through"), not a note bubble (`decisionOf` in `ConversationDetail.tsx`). In the workspace menu at the bottom left, the "superagent" item has the same number beside it (an amber rounded badge); this item is always called "superagent", and when none is set up, clicking it opens the setup dialog (`SuperagentSetup`: start a new Shroom / use an existing agent). On the Mac this item shows ⌘⇧Space on the right. Your superagent is not in the sidebar's Conversations (you find it from this menu and with ⌘⇧Space), and it is not listed when adding agents to a project; in the App it is always called Shroom (`nodeName`, whatever name it gave itself when it joined); its chat has no back button at the top left, and an empty chat shows no suggested questions but a short introduction instead (`SuperagentIntro`: who it is, what it can do for you — hand out work and follow progress, start agents and create projects, see the whole picture, ask you first about what matters — and that it always speaks as itself). Its avatar (`Avatar` in `persona.tsx`; `superagentMark.ts` records which one it is) wears a pixel crown on top (`.pa-crown`, gold, three gems), and its tile has a thin gold outline (`.pa.is-super`).
- **Quick panel** (Mac, ⌘⇧Space, `web/src/quick/Quick.tsx`): a small window that is a single card (640 wide; the 16 corner radius is cut on the window by macOS and the shadow is the system's too; the web page fills the window with no margin, otherwise the WebView is opaque and a white edge shows), with its height following the content. At the top are Shroom's avatar and name, with "Open chat" on the right; it follows the workspace the App is in, so there is no workspace to choose. In the middle, one line of input (15px, ⇧Enter for a new line): Enter sends it, the panel closes and the App opens the chat with Shroom; the answer is read in the chat, and the panel does not show the chat. When there are things waiting for your OK, an amber line under the input box reads "Shroom has N things waiting for your OK · See"; clicking it also opens the chat (where the cards are). At the very bottom, a light line of key hints. Esc or clicking elsewhere closes it. The panel is a floating window that does not activate the App: while it is not the keyboard focus, the WebView swallows the first click, so the native layer forwards every press to the web page (`quick_click_darwin.go`, as for the notch island), and the page acts only once within 600ms. With no superagent set up, it has only one sentence and "Set one up".

### 6.12 Projects: talk with the coordinator, watch the members work beside it

`ProjectSpace.tsx`. The user talks to only one party: the project's **coordinator**. It splits up the work and hands it out; the exchanges between members are a record, not the home page.

- **The home page is your one-to-one chat with the coordinator** (`HomeView`). At the top are the project's name and goal, with two small icons on the right: All activity and Project notes (icons only; the hover text says what they are); below that comes the chat itself, **with no title bar of its own** (the project title already says where you are; naming the coordinator again would repeat it). **A project with any agent always has a coordinator**: the first agent to join becomes the coordinator automatically; for older projects without one, the earliest-joined agent is saved as the coordinator when the project is opened; when the coordinator is removed, the next earliest takes over. The role is stored in the project (an agent sees that it is `[coordinator]` when it is woken), not just a label in the interface. Right-click a member in the right pane and choose "Make it the coordinator" to change it.
- **Handoff cards** (`Handoff.tsx`): what two agents say to each other is **not drawn as bubbles in your chat** (otherwise it looks as if it were talking to you); one exchange is collapsed into a card, inserted in the chat at the time it started. The card's first line: "To [avatar] X" (handing out work, or a note), or the other way round, "[avatar] X From" (work or a note coming in); then the first line of the content · Queued / Working / Handed back (the other side finished) / Done (it finished itself) / Didn't work / Note · the time; once the other side hands back a result, one more line appears below: "↩ first line of the result". Only the handoff and its result are shown: the progress, steps and back-and-forth additions in between do not appear in your chat, and notes going back and forth in the same thread are merged into one card. Only "Working" stands out (the accent colour, a small dot breathing before it); Done, Handed back, Waiting and Queued are grey, and a finished card's words (and its result line) go quiet too; Didn't work stays red and No activity amber. Clicking a card opens their complete exchange (a read-only observer view, where the progress and steps are), in the right pane beside the coordinator, or as a full page when narrow; opened from a card inside a chat (in the same pane), its top-left back button says "Back to X" and returns to that chat, not to the project home (UI smoke "项目 · 插话排在后面"). Only between agents: messages a person sends it are bubbles as usual. The phone (iOS) is the same: the project page and member chats have the same cards (`HandoffCard`, two lines: who to whom, the first line of the content, the state; once handed back, one more line with the result), and opening one shows their exchange page (`ExchangeScreen`, read-only, no input box): the side that gave the work is on the right, the side doing it on the left, with its steps.
  - **Project home** (you and the coordinator): the work the coordinator hands out, and the tasks and notes members **send to the coordinator** (not visible before), are all handoff cards, so it reads: you say something → it hands out work → a card comes back → it sums up for you. All cards are shown, in an empty chat too (in time order), so a string of cards does not suddenly pop up as soon as you send a message; while earlier messages are not loaded yet, cards older than the first loaded message appear once those are loaded. When the coordinator is not woken by the runner (for example it stays in `myco inbox wait`), the threads it opens carry no project, so the project's activity also counts threads **between project members that belong to no project**; otherwise the work it has just handed out would not be visible.
  - **Member chat** (you and one member): what it sends to other agents and what they hand to it are all handoff cards, every other AI it worked with (its peers), not only this project's members (a terminal's commands, such as an agent running `ls` on demo-shell, are its tools at work and stay out, unless the project lists that terminal); the messages between you and it are bubbles as usual. Older ones load as you scroll up, yours and the others' together (each one's page before the oldest shown), so a member that only works with agents never stops at its newest few cards.
- **Clicking a member opens another pane on the right** (`PaneGrid` in `Panes.tsx`). The chat with the coordinator on the left stays open; the right pane shows **all the work** of this member: every task it received (from the coordinator and from you, ordered together by time; tasks from others are marked on the right with who sent them) and its replies (replies to others are marked "To X"), each task still with its work steps below it. Sending a message here hands it work directly; it queues the tasks and handles them in order, and the coordinator is not notified. For a computer, the right pane opens its terminal.
- The title bars of the left and right panes are the same height (`--pane-head-h`, 60px, used by the title bars of every chat and project), so their bottom edges line up side by side.
- **Four panes at most** (`Panes.tsx`): projects and Conversations work the same way: at most four panes, split according to where you drag (like split windows in an editor: a binary tree of left / right and top / bottom splits). The first pane belongs to the place itself (the chat with the coordinator, the Conversations list, or a chat opened from it); the others are members opened separately.
  - Clicking a member: if it is already open, focus jumps to it; otherwise it replaces the pane last clicked (the first time, a pane opens on the right), as with the old two panes.
  - Opening another pane: right-click a member (in the member pane, in the row of avatars when it is collapsed, or in the sidebar's Conversations list) and choose "Open in a new pane": the largest pane is split in half along its long side (a wide one left and right, a tall one top and bottom).
  - Dragging in: dropping on the left / right / top / bottom edge of a pane splits only that pane (with two panes side by side, dropping on the bottom edge of the left pane makes the left pane two stacked panes, and the right pane stays as it is); dropping on the outermost edge of the whole chat area (within about 22px) adds a pane on that side of the whole ("A new pane across the bottom"); dropping in the middle of a pane is "Show it here instead" (not for the first pane). Before you let go, the area it would land in lights up and says what will happen; where it cannot go, the area is grey and gives the reason ("Four panes at most: drop on one to show it there instead"). The new pane shares space equally with the existing panes in the same direction (with two already stacked below, the new one takes a third).
  - When a member that is already open (in a separate pane, or the first pane is already the chat with it) is dragged in, the pane it is in lights up amber with "X is open already", and letting go does not open it again; "Open in a new pane" on someone already open only jumps to it with a brief flash.
  - The vertical and horizontal lines between panes can all be dragged (15%–85%, double-click to go back to half), and each line handles only the two parts it divides; each pane's title has "Show only this pane" on the right (click again: "Back to all the panes"), and separately opened panes also have a close button; when a pane is closed, the part that was split together with it fills the space.
  - When they do not fit (each pane at least 320×240), the panes become tabs: a row of tabs at the top (names; separately opened ones with ×), one pane shown at a time, with the newly opened pane selected. With "Show only this pane", no tabs appear.
  - The member list collapses into a row of avatars under the left pane's title only when there is no room for "panes side by side (each at least 320px) plus the member list"; otherwise it stays put, so the page does not jump when you open a member. A newly opened pane fades in briefly; when a pane moves, the chat in it does not reload (each pane stays mounted).
  - Which panes are open and how they are split is stored on this computer, separately for each project and for Conversations; clicking the project again in the sidebar goes back to the first pane only. The right pane fades in when it opens; when loading is fast, no placeholder block flashes (it shows only after 0.2 seconds). Dragging a divider follows the distance the pointer moves, so it does not jump to the pointer on press.
- **All activity**: the former group-chat card stream, read-only, no input box, back at the top left. It is kept for looking back at what the members did between themselves. Clicking a card also opens the corresponding member in the right pane.
- **The input box shares the chat's column**: the chat content and the input box below it share one width and left / right padding (`--conv-col` / `--conv-pad` / `--conv-pad-l`; with the turn navigation bar on the left, a little more is left on the left), so their left and right edges line up.
- **A reply must show which message it answers**: when the message before a reply is not the one it answers (for example several tasks taken together and answered together at the end), the reply quotes the original at its top ("You <first line of the original>"), and clicking it jumps there; both in one-to-one chats and when watching the chat between two members.
- **Dividers appear only after a long gap**: only when two messages are more than 30 minutes apart is a divider with the time placed between them; there is no longer a divider at every change of thread.
- **A task's time, tokens and cost** go with its reply, in the row below the reply with the time and the copy button (shown only on hover), not under the steps.
- **Chats must be steady**: when switching sessions, a session you have seen shows its cached content in the first frame (no blank first), and scrolls to the bottom before the screen is painted; when a poll returns unchanged content, there is no redraw and no scroll, and only new messages take a chat that is at the bottom down to the bottom, while one you are reading scrolled up stays put; when task steps or pictures load late and make the content taller, a chat that was at the bottom stays at the bottom. ### 6.15 A feature's pages: list page, detail page, records (build new pages this way)

Automations and workflows were built from this section; a new kind of thing (say a future "Release" or "Dataset") is built the same way; do not start a separate pattern.

**List page** (a top-level entry in the sidebar)

- The page header uses `PageHero`: title 22px / 650, with a one-line explanation below; on the right at most one solid button "New X" (`.app-btn-primary`, default height).
- When there are none at all, the middle of the page explains what this is and lists a few ready-made templates right below; once there are some, the templates move into the "New X" dialog and the list page no longer repeats them.
- The list is in one card, one per row: an icon or status on the left, two or three lines in the middle (name; what it does and who it goes to; the latest result and its time), and on the right two always-visible buttons of the same height: the most common action (`.app-btn-small`, for example "Run") and a square ⋯. Rows have no switch. The right-click menu and ⋯ are the same menu: Open, Edit, Turn off / Turn on, a divider, Delete.

**Detail page**

- No "← Back" button (use the ‹ › in the top bar, see section 8), and no icon block in the page header.
- Left of the page header: the title (22px / 650), with a grey summary line below; first comes the status (`● On`), then the number of steps, the version, the project it belongs to; IDs and paths use `.mono`. On the right: all action buttons at default height, secondary ones on the left ("Edit"), the primary solid button on the right ("Run"), and last a square ⋯ for the less common ones (Turn off / Turn on, Delete).
- Below the page header, tabs (`.wf-tabs`) divide the content; the one looked at most opens by default (the records when there are any; the steps for a new one). Tabs may carry counts.
- Spacing rhythm (`.aud`): page header to tabs 24px, tabs to content 16px, 28px between sections (`.ph-section`). 12px between cards.
- Filters go above the list on the left: a row of small rounded options (`.wf-chips` / `.wf-chip`, the selected one on a dark background, optionally followed by a count); not on the right, and not a drop-down.

**Records** (runs, send records, events)

- Each starts with a round status mark (`RunMark`: green tick done, red cross failed, amber dot waiting for you, green dot running).
- The title is what this run was about, in the sentence a person wrote. Paths, links, file names and IDs are not titles; when there is only those, the title is the start time ("Run · today 09:52"), paths go in small `.mono` on the second line, links show the domain and last segment, full on hover.
- Second line: the status word (first, in its status colour), which step it is on while running, a one-sentence reason when it failed (truncated when too long, full on hover), who started it. Two lines on the right: how long ago, how long it took.
- Clicking one opens its page: the title as in the list, the status first below the title, and what it belongs to (which workflow) written as a link that leads back.

**Menus and deletion**

- Delete in ⋯ and right-click menus is just called "Delete", not "Delete this workflow…" (a click first asks for confirmation, and the confirmation says exactly what is deleted). Normally it has the same colour as the other items, and turns red only on hover or keyboard selection (see 6.6).

## 7. Icons

- The window frame, sidebar, node types and machine types use the hand-drawn icons in `web/src/components/icons.tsx`: 16px grid, stroke width 1.25, round caps and round joins. Draw new ones the same way, and look at them next to the other icons in the sample sheet.
- Action icons inside pages (search, plus, edit, copy and so on) use lucide, with the stroke width set to 1.75 for all of them by the styles; do not pass `strokeWidth` to a single icon.
- Official app SVG icons are rendered as alpha masks in the text color (`.tp-svg`). Use transparent backgrounds and outline artwork; an opaque background turns the whole icon into a solid tile. Check the mask in light and dark appearances.
- Sizes: 16px in the top bar and sidebar, 18px in list rows, 14px inside buttons, 14px for section actions.
- One shape means one thing: pen = edit, bubble with a plus = new chat, plus = add, `«` `»` = collapse and expand a pane.
- Do not draw third parties' official logos; tell the vendors' CLIs apart with generic shapes (Claude: asterisk, Codex: code brackets, Gemini: four-pointed star, Cursor: pointer).

## 9. Copy

- Every sentence gives both languages at once with `L("中文", "English")`.
- Buttons and menu items do not end with "…". Only in-progress states use it ("Starting…").
- Buttons say a verb and an object ("Add an agent", "Start a chat"), not "OK" or "Submit".
- Explanatory text speaks plainly and says it in one sentence; no API names or field names.
- Settings pages use no large areas of red or green: write a status as text, like "● Connected"; buttons such as remove and stop are outlined neutral buttons normally and turn red only on hover; solid red is kept for the final step in a confirmation dialog.
- Fixed terms (the Chinese copy): 工作区 (workspace), 项目 (project), agent (成员, member), 电脑 (computer), 单聊 (one-to-one chat), 任务 (task), 补充 (addition), 排队中 (queued). Do not call one thing by different names. Do not use 节点 (node), 机器 (machine), Hub or runner (see section 0).
- Times are relative ("5 min ago"); when the exact time is needed, put it in the hover tooltip.

## 10. Dark mode

- Build both modes and look at both. When all colours go through variables, they adapt automatically.
- In dark mode, hierarchy is shown by being "brighter", not by shadows; in light mode, by shadows and white.
- When a translucent overlay is needed, use `color-mix(in srgb, var(--fg) N%, transparent)`; do not hard-code black or white.

## 11. Don'ts

- Do not use green for button backgrounds, icon colours or decoration.
- Do not put dividers between list rows, and do not wrap the content of a panel in another bordered box.
- Do not use controls with the system's native look (dropdowns, checkboxes) without styling them.
- Do not add `cursor: pointer` (except on text links) or hover `transition`s.
- Do not add breadcrumbs or refresh buttons.
- Do not put two solid buttons on one screen.
- Do not hand-edit `internal/web/dist`.

## 12. When you are done

```bash
cd web && npm run typecheck
cd web && npm run test:ui     # screenshots every page at two widths, light and dark, into web/ui-smoke/ (about 2 minutes)
make web                      # regenerates internal/web/dist; commit it
make vet && make test
```

`test:ui` first builds the App once (a few seconds), then runs the four "width × light / dark" combinations at the same time, each with its own mock backend and ports (mock from 7781 and App from 5173, one port each), so they do not interfere; at the end it lists the slowest steps. While you work you can run only the relevant steps, and run them all before you commit:

```bash
npm run test:ui -- --only 单聊              # only the steps whose names contain "单聊" (one-to-one chat); several allowed
npm run test:ui -- --combo 1200-light       # only one combination (1200-light, 1200-dark, 760-light, 760-dark)
npm run test:ui -- --serial                 # one combination after another, so the log is easy to read
```

Before you commit, look through the screenshots yourself and check at least:

- [ ] Both light and dark have been checked.
- [ ] Both 1200 wide and 760 wide have been checked, and nothing is squashed in the narrow window.
- [ ] All four states are there: hover, pressed, disabled, keyboard focus.
- [ ] All four cases have a design: empty, loading, error, no search results.
- [ ] New rows have a right-click menu, and new icon buttons have a `title`.
- [ ] The copy is written in both Chinese and English, and no button has "…".
- [ ] No new hard-coded colour values, no new font sizes.
- [ ] The page is built as in 6.15: detail pages have no back button and no icon block, page header buttons are all the default height with none set separately, rows and page headers have no switches, filters are on the left.
- [ ] Record titles are plain words, not paths or IDs.
- [ ] Delete in menus is called just "Delete", and is not red normally.
- [ ] Dialogs: buttons are not stuck to the bottom, there is no divider under the tabs, waiting and what is missing are written to the left of the buttons, and a tab reads "short label → content → small text".
- [ ] New pages or dialogs have been added to `web/scripts/ui-smoke.mjs`, and the mock data (`web/mock/app-server.mjs`) has matching content.

How the interface really looks on the Mac (traffic-light alignment, fonts, right-click menu position) has to be checked with a preview build; maintainers build one with the myco-preview skill in their internal repository.

The "Allow MCP tools" item in the run settings is shown only to people who own the node, and only when its runner reports the `mcp_tools` feature; it is off by default. With full access it shows as on but cannot be changed, with an explanation that MCP tools are already allowed.

### Remote Desktop app

The entry lives in Apps, with no new Computers navigation. Use neutral surfaces,
subtle borders and monochrome actions in both appearances. Two tabs: Connect to a
computer (searchable available-host cards) and Share this computer (optional
component installation, view-only default, explicit sharing, private temporary
pairing code and Stop sharing). Settings offers component status and uninstall.
Follow the App's language and theme. Never seed real-looking connection history,
store credentials in records or claim that a fixture is a live connection.

The embedded app cannot approve its own install/connect/share operation: a
trusted App modal explains the requested access. Closing, reloading or changing
the language ends the page's sessions; hiding a tab leaves it running. Show
connection progress, errors, real media statistics and a visible Disconnect.
The initial version explicitly labels its LAN/Tailscale, no-audio and unlocked-
desktop limitations. Optional media dependencies do not link into core myco.

### Public-access setup and readiness

Tailscale Funnel is selectable even if missing. Its setup card offers neutral
platform buttons, official downloads, copyable install/start commands and an
agent handoff prompt. The person completes account sign-in, OS network approval,
and initial Funnel authorization. Check again refreshes executable detection
without resetting the selected option. Only a nonempty valid public URL and a
passing public health check count as success; otherwise retain local access,
show an actionable error, and allow retry. Cancelled requests cannot reopen a
success panel later.

Once Tailscale is detected, the installation card is hidden. If opening fails,
its sign-in and permission troubleshooting guidance becomes available again.

项目成员设置中的「邀请 agent」开关默认关闭，项目主人或管理员可更改。关闭时，协调者的邀请在现有批准卡中展示项目和预填的 agent 资料，并明确说明一次性、24 小时、归项目主人所有和普通成员权限；批准卡不含邀请凭据。成员资料显示邀请来源。旧 Hub 未提供此字段时隐藏设置。

项目成员页用「协调者的权限」一组展示电脑启动、邀请和定时任务授权，定时任务默认关闭。批准卡展示具体操作、任务、收件人、时间范围和只跑一次，并明确只批准当前变更。自动化编辑器按本机时间输入有效期，列表与详情显示起止时间、一次性执行和到期/已执行/项目范围变更的停用原因；旧 Hub 保持普通编辑可用。

### Removing a workspace during a refresh

Removing a workspace closes its current views immediately. Reads started before
the removal cannot restore its workspace list, overview or projects when they
finish. Leaving the usage page, switching workspaces or changing its filters
cancels the outstanding usage request. The UI smoke removal scenario keeps
Usage open behind Settings and releases an older refresh after removal.

### Browser control approvals

A live browser control request names the browser profile and the duration.
The approval defaults to the dedicated agent profile. A personal profile
shows its name and a prominent warning that the agent can see and operate
sites the owner is signed in to. The card says that actions appear on the
owner's screen and that the owner can stop control at any time.

List each requested domain as a checked option the owner can remove. Disable
approval if all requested domains are removed. When the request has no domain
scope, show “No domain restriction.” The UI smoke scene checks both profile
types and verifies that only the selected domain is sent when approving.
